# Partial Clone: On-Demand Git Object Fetching

## What you will learn

- Explain what a partial clone is: download only the objects you need, fetch the rest on demand from a promisor remote
- Use `--filter=blob:none`, `--filter=tree:0`, and `--filter=blob:limit=<size>` and pick the right trade-off
- Combine partial clone with sparse checkout to shrink a monorepo's initial footprint
- Know when partial clone helps (large repos, slow clones) and when it hurts (offline work, tools that need all blobs)


## Start with a problem

Your Git repository keeps growing, clones are getting slower, and everyday operations are starting to feel sluggish. You want to know what optimization techniques are available and which ones fit your project.

## One-Sentence Understanding

Partial clone lets you clone a repository downloading only the Git objects you need, fetching others on-demand — like lazy loading for Git.

## How It Works

### Filter

At clone/fetch time, specify which objects to exclude:

```bash
git clone --filter=blob:none <url>
```

### Promisor Remote

Filtered objects aren't lost — Git knows which remote can provide them. When needed, Git automatically fetches from the promisor remote:

```bash
# This is a partially cloned repo
cd repo

# The workspace is nearly empty, but metadata is local
git checkout main
# → Git auto-fetches file contents from the remote
```

## Filter Types

### blob:none

Exclude all blob objects (file contents), download only commit, tree, and tag objects:

```bash
git clone --filter=blob:none <url>
```

- Reduces initial download by 70-90%
- First checkout needs network
- Best for general use

### tree:0

Exclude tree and blob objects, download only commits:

```bash
git clone --filter=tree:0 <url>
```

- Minimal initial download
- Most operations require remote requests
- Best for log/metadata only

### `blob:limit=<size>`

Exclude blobs larger than the limit:

```bash
git clone --filter=blob:limit=1m <url>
```

### Combining Filters

```bash
git clone --filter="combine:blob:none+tree:0" <url>
```

## Practical Guide

### Clone a Partial Clone Repo

```bash
# Standard partial clone
git clone --filter=blob:none https://github.com/example/large-repo.git

# With sparse checkout
git clone --filter=blob:none --sparse https://github.com/example/large-repo.git
cd large-repo
git sparse-checkout set src/my-team
```

### Enable in Existing Repo

```bash
git config core.repositoryformatversion 1
git config extensions.partialClone origin

# Remove all local blob objects
git rev-list --objects --all | git pack-objects --stdout | git pack-objects --stdin --keep-unreachable
git prune
```

### Manual Fetch

```bash
# Trigger promisor fetch
git fetch --refetch

# Auto-fetch missing blobs
git cat-file -p <blob-hash>
```

## Performance

| Scenario | Full Clone | blob:none | Savings |
|----------|-----------|-----------|---------|
| Initial download | 500MB | 50MB | 90% |
| git log | Fast | Fast | Same |
| git checkout | Fast | Needs fetch | Slower |
| git status | Fast | Needs fetch | Slower |

## Limitations

- Network dependency for first checkout and diffs
- Server-side support: GitHub ✓, GitLab 13.6+ ✓, Bitbucket limited
- `git gc` needs special handling
- Some tools and old IDE integrations may not be compatible

### Revert to Full Clone

```bash
git fetch --unshallow
git config --unset extensions.partialClone
```

## Try it yourself

1. **Compare the three filters on first clone**: clone the same large repo with `--filter=blob:none`, `--filter=tree:0`, and `--filter=blob:limit=1m`, record the initial download size of each, then `git checkout main` and watch which operations trigger on-demand fetches.
2. **Combine partial clone with sparse checkout**: `git clone --filter=blob:none --sparse <url>` then `git sparse-checkout set src/my-team`, and confirm the local repo neither downloaded all blobs nor expanded directories you do not care about — the most direct speed-up for a monorepo.
3. **Drill the rollback to a full clone**: in a partial clone, run `git fetch --unshallow` to pull every object, then `git config --unset extensions.partialClone` to turn partial cloning off, and use `git fsck` to confirm all objects are now local.

## A detail easy to miss: partial clone does not slow down history commands

`--filter=blob:none` only filters file contents (blobs); commit, tree, and tag history objects are still downloaded in full. So commands that only read history — `git log`, `git branch --contains`, `git rev-list` — run at almost the same speed as in a full clone. What actually gets slower are operations that must materialize content into the working tree: `git checkout`, `git diff` against the working tree, or a full `git grep`. Understand this and you can judge whether partial clone will actually help your scenario.
