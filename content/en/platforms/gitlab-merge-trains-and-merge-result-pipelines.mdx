# GitLab merge trains and merged result pipelines

## What you will learn

- Understand the distinct roles of merged-result pipelines and merge trains, and why a green per-branch CI does not mean green after merge
- Enable a merge train in a GitLab project, including the `.gitlab-ci.yml` config and the `$CI_MERGE_REQUEST_ID` rule
- Recognize which high-concurrency merge scenarios call for a merge train and which lightweight cases do not


A branch pipeline passing does not guarantee the post-merge combination will stay green. Merge trains target that integration gap.


## Start with a problem

You and a teammate merged two MRs into `main` almost at the same time. Both pipelines were green on their own, yet CI went red right after merge — you touched the same module, and neither branch saw the other's change in isolation. The tests weren't wrong; the *combined post-merge result* was never verified. That gap is exactly what merge trains close.

## Two core pieces

- merged result pipeline: CI on the merge outcome
- merge train: ordered queue for MR integration

## Best-fit scenarios

1. high merge concurrency on one protected branch
2. frequent “base changed” pipeline churn
3. strong requirement for stable mainline

<WarningBox title="Queueing is orchestration, not quality replacement">
  Merge trains reduce merge race risk, but still depend on meaningful test coverage.
</WarningBox>

## How to enable (minimal config)

A merge train requires **merged result pipelines** to be on first, then the train itself (both toggled in Settings → Merge requests).

In `.gitlab-ci.yml`, make the pipeline run on the merge result rather than only on the source branch:

```yaml
# Run the pipeline on the MR's merge result (merged result pipeline)
# With merge trains on, GitLab also folds in the results of prior queued MRs
test:
  script: ./run_tests.sh
  rules:
    - if: $CI_MERGE_REQUEST_ID

# While a merge train runs, the pipeline faces the train ref:
# refs/merge-requests/<iid>/train
```

<WarningBox title="The train ref is not your branch">
  The Nth MR in the queue runs against a temporary combination where the previous N-1 MRs are already merged — not the branch you pushed. Don't hardcode branch names in assertions.
</WarningBox>

### Adding an MR to the train queue

- In the MR page click **Start/Add to merge train** (merge permission required)
- Or via API: `POST /projects/:id/merge_trains/merge_requests/:merge_request_iid`
- If any MR's train pipeline fails, it and the MRs behind it are dropped from the queue and must be re-run from the failure point

## Try it yourself

1. In a test project, turn on merged result pipelines + merge train, then create two conflicting MRs on purpose and watch how they enter the train queue instead of merging separately.
2. Rewrite one existing pipeline in `.gitlab-ci.yml` using the `$CI_MERGE_REQUEST_ID` rule, and compare the output of "source branch only" vs "merge result".
3. Force a train pipeline of one MR to fail, observe the trailing MRs being dropped from the queue, and practice re-running from the failure point.
