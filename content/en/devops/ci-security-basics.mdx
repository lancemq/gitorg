# Git Security Basics in CI/CD

## What you will learn

- Understand how Git security risks in CI/CD differ from local dev (automation, credential injection, third-party dependencies)
- Manage credentials with Secrets / Variables and least privilege, and keep tokens out of logs
- Use branch protection, restricted CI triggers, and commit signature verification to block injection and tampering
- Build an auditable habit for CI Git operations — what to log and what to review regularly



## Start with a problem

CI runs unattended on machines that can pull code, run scripts, and push or deploy with a token. If a third-party Action silently prints your `DEPLOY_KEY` to logs, or someone edits your CI config in a PR to run malicious commands, you may not notice — but an attacker may already have write access. Git security in CI comes down to two things: limiting credential exposure and guarding the trust boundary that is your pipeline config.

## One-Sentence Understanding

Git security in CI/CD is about limiting the credential attack surface in an automated, unattended environment and defending the trust boundary that is your pipeline configuration.

## Overview

Git operations in CI/CD pipelines face different security risks than local development: automated execution, credential injection, and third-party dependencies all introduce new attack surfaces.

## Core Risks

| Risk | Description | Impact |
|------|-------------|--------|
| Credential leak | Token or key written to logs | Malicious push to repo |
| Branch injection | Attackers modify CI config via PR | Pipeline executes malicious code |
| Dependency confusion | Third-party Action/Plugin steals data | Credentials stolen |
| History tampering | Force push overwrites shared history | Code loss or injection |

## Credential Management

### GitHub Actions

```yaml
# Use Secrets, never hardcode
jobs:
  deploy:
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Deploy
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
        run: ./deploy.sh
```

### GitLab CI

```yaml
# Use CI/CD Variables
deploy:
  script:
    - echo "$DEPLOY_KEY" | base64 -d > deploy_key
    - chmod 600 deploy_key
    - ssh -i deploy_key user@server "deploy"
```

### Principle of Least Privilege

- Use dedicated credentials per pipeline
- Scope credentials to the smallest set of repos
- Rotate credentials regularly
- Never output credentials to logs

<WarningBox title="Third-party Actions can read your Secrets by default">
  In GitHub Actions, `uses: some-org/some-action@v1` runs someone else's code. If that Action prints `${{ secrets.XXX }}` to logs, the secret leaks. Pin Actions to a specific commit SHA, prefer officially maintained ones, and mark critical secrets "Protected" so they're only available on protected branches.
</WarningBox>

## Branch Protection

### Prevent Direct Push to Main

```yaml
# GitHub branch protection rules
# - Require PR before merging
# - Require status checks to pass
# - Require signed commits
```

### Restrict CI Triggers

```yaml
# GitHub Actions - only trusted PRs
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
```

## Signature Verification

```yaml
# Verify commit signatures in CI
jobs:
  verify:
    steps:
      - uses: actions/checkout@v4
      - name: Verify commits
        run: |
          git log --show-signature -1
```

## Audit Trail

- Enable Git operation audit logs (supported by GitHub/GitLab)
- Log all Git operations triggered by CI
- Review CI config modification permissions regularly

## Try it yourself

1. In a test repo, add a CI step that does `echo "$DEPLOY_KEY"`, run it, and check the logs to see whether the value is masked; if not, switch it to a protected variable and re-verify.
2. Enable branch protection on `main` (require PR + status checks), then try a direct push and confirm it's rejected.
3. Open a PR from a fork that edits `.github/workflows`, and observe whether your base repo's CI auto-runs the forked changes — understand why external PRs should not get repo secrets by default.
