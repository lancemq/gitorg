# GitLab CI & Git Integration

## What you will learn

- Understand how GitLab CI keeps pipeline definitions in `.gitlab-ci.yml`, so build config lives in the repo alongside code
- Control pipeline triggers from Git events (push / MR / tag / schedule) and branch-specific behavior with `workflow: rules`
- Know what built-in variables and strategies like `CI_JOB_TOKEN`, `GIT_STRATEGY`, and `GIT_DEPTH` actually change
- Recognize common CI Git security mistakes (leaked credentials, careless force-push from CI) and how to avoid them


## Start with a problem

You push locally, and moments later GitLab automatically runs tests, builds, even deploys. But have you ever asked how the pipeline's Git actually gets the code — where its credentials come from, where it can push, and how that differs from typing commands in your terminal? Those differences are exactly where CI pipelines go wrong, and exactly what's worth understanding.

## One-Sentence Understanding

GitLab CI/CD treats Git as the single source of truth for your entire DevOps lifecycle, from pipeline triggers triggered by pushes to automatic deployment triggered by tags.

## Pipeline Triggers

GitLab CI can be triggered by various Git events:

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "push"
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_PIPELINE_SOURCE == "tag"
    - if: $CI_COMMIT_TAG
```

### Branch-Specific Rules

```yaml
stages:
  - test
  - deploy

test:
  stage: test
  script: npm test

deploy:
  stage: deploy
  script: npm run deploy
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_COMMIT_TAG
```

## Git Strategy in CI

### GIT_STRATEGY Options

| Strategy | Behavior | Use Case |
|----------|----------|----------|
| `clone` | Full clone each time | Clean builds |
| `fetch` | Fetch + reset from cache | Faster, use for small changes |
| `none` | Don't fetch | Reuse previous workspace |

```yaml
variables:
  GIT_STRATEGY: fetch
  GIT_DEPTH: "50"       # Shallow clone for speed
  GIT_SUBMODULE_STRATEGY: recursive
```

## GitLab CI Variables from Git

GitLab provides rich CI/CD variables derived from Git:

```yaml
script:
  # Commit info
  - echo "Commit: $CI_COMMIT_SHA"
  - echo "Short SHA: $CI_COMMIT_SHORT_SHA"
  - echo "Branch: $CI_COMMIT_BRANCH"
  - echo "Tag: $CI_COMMIT_TAG"
  - echo "Message: $CI_COMMIT_MESSAGE"

  # Author info
  - echo "Author: $GITLAB_USER_NAME"
  - echo "Email: $GITLAB_USER_EMAIL"

  # Merge request info
  - echo "MR: $CI_MERGE_REQUEST_IID"
  - echo "Source branch: $CI_MERGE_REQUEST_SOURCE_BRANCH_NAME"
```

## Running Git Commands

```yaml
before_script:
  - git config user.name "gitlab-ci"
  - git config user.email "ci@gitlab.com"

script:
  - git fetch --tags origin
  - VERSION=$(git describe --tags --abbrev=0 2>/dev/null || echo "v0.0.0")
  - echo "Current version: $VERSION"
```

## CI_JOB_TOKEN

GitLab provides `CI_JOB_TOKEN` for authenticating Git operations:

```yaml
# Push to a different repository
script:
  - git remote add target https://gitlab-ci-token:${CI_JOB_TOKEN}@gitlab.com/org/target.git
  - git push target main
```

<WarningBox title="Never commit long-lived credentials in .gitlab-ci.yml">
  `CI_JOB_TOKEN` is short-lived and auto-rotated — use it only inside the pipeline. Real deploy keys and cloud secrets belong in protected, masked CI/CD Variables, never in the repo. Anything written into the repo enters Git history and is hard to fully erase.
</WarningBox>


### Token Scope

| Scope | Permission |
|-------|-----------|
| Same project | Read + write |
| Same group | Configurable |
| Cross-project | Must configure |

## Workflow Rules

Control pipeline execution based on Git context:

```yaml
workflow:
  rules:
    - if: $CI_COMMIT_TAG
      variables:
        PIPELINE_TYPE: "release"
    - if: $CI_COMMIT_BRANCH == "main"
      variables:
        PIPELINE_TYPE: "deploy"
    - if: $CI_MERGE_REQUEST_ID
      variables:
        PIPELINE_TYPE: "merge_request"
    - when: always
```

## Environment Management

GitLab Maps Git branches and tags to environments:

```yaml
deploy_staging:
  stage: deploy
  script: deploy-to-staging
  environment:
    name: staging
    url: https://staging.example.com
    deployment_tier: staging
  rules:
    - if: $CI_COMMIT_BRANCH == "develop"

deploy_production:
  stage: deploy
  script: deploy-to-prod
  environment:
    name: production
    url: https://example.com
    deployment_tier: production
  rules:
    - if: $CI_COMMIT_TAG
```

## Try it yourself

1. In a test repo, add a minimal `.gitlab-ci.yml` with one `build` stage running `npm ci && npm test`, push, and watch the pipeline trigger automatically.
2. Add `workflow: rules` so `main` gets production variables and `develop` gets staging variables; verify the injected variables really differ per branch.
3. Set `GIT_DEPTH` very small (e.g. `5`), then run a script that depends on an older commit beyond that depth — see how "not enough history" breaks history-dependent steps.
