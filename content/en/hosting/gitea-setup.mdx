# Gitea Self-Hosted Git Service

## What you will learn

- Understand Gitea's positioning: a lightweight self-hosted Git service for small teams / individuals, far lighter than GitLab CE
- Install via binary or Docker and complete the key settings on the first-run setup page
- Back up daily with `gitea dump` and run a basic upgrade without losing data
- Make a preliminary choice between Gitea, GitLab CE, and GitHub based on team size



## Start with a problem

You want code hosting on a machine you fully control — maybe to keep data inside your network, or because GitHub's private repos feel limiting while GitLab CE feels too heavy. Gitea sits in the middle: one binary runs, 128MB of RAM is enough. But can it really support your team's daily collaboration? This guide gets it installed, configured, and helps you know when to switch to something heavier.

## One-Sentence Understanding

Gitea is a lightweight, Go-written self-hosted Git service that runs from a single binary, lowering the barrier to "your own code repository" to almost nothing.

## Overview

Gitea is a lightweight self-hosted Git service written in Go. Compared to GitLab CE, Gitea has minimal resource requirements (128MB RAM is enough), making it ideal for small teams or personal use.

## Installation

### Method 1: Binary Install (Recommended)

```bash
# Download the latest binary
wget -O gitea https://dl.gitea.com/gitea/1.22/gitea-1.22-linux-amd64
chmod +x gitea

# Create the git user
sudo adduser --system --group --disabled-password --shell /bin/bash --home /home/git git

# Create required directories
sudo mkdir -p /var/lib/gitea/{custom,data,log}
sudo chown -R git:git /var/lib/gitea
sudo chmod -R 750 /var/lib/gitea

# Start
sudo -u git ./gitea web
```

### Method 2: Docker Deployment

```yaml
# docker-compose.yml
version: "3"
services:
  gitea:
    image: gitea/gitea:1.22
    ports:
      - "3000:3000"
      - "222:22"
    volumes:
      - ./gitea-data:/data
    restart: always
```

```bash
docker compose up -d
```

## Initial Configuration

Visit `http://localhost:3000` in your browser — the installation page appears:

| Setting | Recommended |
|---------|-------------|
| Database | SQLite (small team) or PostgreSQL |
| Domain | Custom domain or IP |
| SSH port | 222 (if using Docker port mapping) |
| HTTP port | 3000 |
| Admin account | Create immediately |

## Daily Administration

### Backup

```bash
# Built-in backup command
sudo -u git ./gitea dump -c /etc/gitea/app.ini

# Backup includes: database, repos, config, logs
# Output to /var/lib/gitea/data/
```

### Upgrade

```bash
# 1. Stop service
sudo systemctl stop gitea

# 2. Backup
sudo -u git ./gitea dump

# 3. Replace binary
cp gitea-old gitea-new

# 4. Restart
sudo systemctl start gitea
```

### Configuration

```INI
# /etc/gitea/app.ini
[server]
DOMAIN = git.example.com
ROOT_URL = https://git.example.com/
HTTP_PORT = 3000
SSH_DOMAIN = git.example.com

[database]
DB_TYPE = sqlite3
PATH = /var/lib/gitea/data/gitea.db

[mailer]
ENABLED = true
SMTP_ADDR = smtp.example.com
```

<TipBox title="Put Gitea behind a reverse proxy and force HTTPS in production">
  Using `http://` in `ROOT_URL` is for demo only. In production, place Gitea behind Nginx / Caddy, terminate TLS there, and set `ROOT_URL` to `https://`. If you map SSH via Docker (`222:22`), keep `SSH_DOMAIN` consistent with the clone URL or others will connect to the wrong port.
</TipBox>

## Comparison

| Feature | Gitea | GitLab CE | GitHub |
|---------|-------|-----------|--------|
| Memory | ~128MB | ~4GB | SaaS |
| Setup complexity | Low | High | None |
| CI/CD | Built-in Actions | Built-in CI | Actions |
| Code review | Yes | Yes | Yes |
| Team management | Basic | Rich | Rich |
| Migration tools | Yes | Yes | Yes |

## Try it yourself

1. Launch Gitea with Docker Compose (map `3000` for HTTP, `222` for SSH), finish the first-run setup in the browser, create a test repo, and clone it successfully.
2. Run a `gitea dump` backup and confirm the artifact includes the database and repo data; then simulate an upgrade (swap the binary + restart) and verify the data survived.
3. Create an organization and a member account in Gitea, compare permissions with a pure personal repo, and use the comparison table to judge whether it fits your team size.
