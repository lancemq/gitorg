## Start with a problem

Your understanding of Open your first pull request may stop at "I know how to run it" — but not why it's designed this way or where its boundaries are. Those blurry spots are exactly where things break. This article moves you from "can use" to "understands" Open your first pull request.

## Pre-PR checklist

1. changes are scoped to one objective
2. branch is synced with latest mainline
3. commit messages are readable

## Minimal sequence

```bash
git fetch origin
git rebase origin/main
git push -u origin feature/first-pr
```

Then open a PR with:

- intent and expected outcome
- key change points
- risk and validation notes

<WarningBox title="A PR is a collaboration interface, not just a code upload">
  Missing context increases review round-trips and slows merge decisions.
</WarningBox>
