# CI/CD 中的 Git 安全基础

## 学完这篇你会掌握什么

- 理解 CI/CD 里 Git 操作的安全风险和普通开发环境有何不同（自动化、凭据注入、第三方依赖）
- 掌握凭据管理（Secrets / Variables）、最小权限原则，避免 Token 泄露到日志
- 知道如何用分支保护、CI 触发限制、提交签名验证挡住常见的注入与篡改
- 建立"可审计"的 CI Git 操作习惯，知道要记录什么、定期审查什么



## 先想一个问题

CI 跑在无人值守的机器上，能自动拉代码、跑脚本、还能拿着令牌去推送甚至部署。如果某个第三方 Action 偷偷把你的 `DEPLOY_KEY` 打印到日志，或者有人在 PR 里改了你的 CI 配置去执行恶意命令——你未必会立刻发现，但攻击者可能已经拿到了仓库的写权限。CI 里 Git 的安全，核心就是管住"凭据"和"谁能改流水线"这两件事。

## 一句话理解

CI/CD 中的 Git 安全，本质是"在自动化、无人值守的环境里，限制凭据的暴露面，并守住流水线配置这道信任边界"。

## 概述

CI/CD 管道中 Git 操作的安全风险与普通开发环境不同：自动化执行、凭据注入、第三方依赖等因素都会引入新的攻击面。

## 核心风险

| 风险 | 描述 | 影响 |
|------|------|------|
| 凭据泄露 | Token 或密钥被写入日志 | 仓库被恶意推送 |
| 分支注入 | 攻击者通过 PR 修改 CI 配置 | 管道执行恶意代码 |
| 依赖混淆 | 第三方 Action/Plugin 窃取数据 | 凭据被窃取 |
| 历史篡改 | Force push 覆盖共享历史 | 代码丢失或注入 |

## 凭据管理

### GitHub Actions

```yaml
# 使用 Secrets 而非硬编码
jobs:
  deploy:
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Deploy
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
        run: ./deploy.sh
```

### GitLab CI

```yaml
# 使用 CI/CD Variables
deploy:
  script:
    - echo "$DEPLOY_KEY" | base64 -d > deploy_key
    - chmod 600 deploy_key
    - ssh -i deploy_key user@server "deploy"
```

### 最小权限原则

- 每个管道使用独立的凭据
- 凭据 scope 限定到最小仓库集合
- 定期轮换凭据
- 禁止在日志中输出凭据

<WarningBox title="第三方 Action 默认就能读到你的 Secrets">
  在 GitHub Actions 里，`uses: some-org/some-action@v1` 会执行别人的代码。如果该 Action 把 `${{ secrets.XXX }}` 打印到日志，密钥就泄露了。原则：锁定 Action 版本到具体 commit SHA、优先使用官方维护的 Action、对关键密钥开启 "Protected"（仅受保护分支可用）。
</WarningBox>

## 分支保护

### 禁止直接推送到主干

```yaml
# GitHub branch protection rules
# - Require PR before merging
# - Require status checks to pass
# - Require signed commits
```

### 限制 CI 触发条件

```yaml
# GitHub Actions - 只信任的 PR 触发
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
```

## 签名验证

```yaml
# 在 CI 中验证提交签名
jobs:
  verify:
    steps:
      - uses: actions/checkout@v4
      - name: Verify commits
        run: |
          git log --show-signature -1
```

## 审计与日志

- 启用 Git 操作审计日志（GitHub/GitLab 均支持）
- 记录所有 CI 触发的 Git 操作
- 定期审查谁有权限修改 CI 配置

## 给你的练习

1. 在一个测试仓库配置一条会 `echo "$DEPLOY_KEY"` 的 CI 任务，运行后去日志里找这个变量——确认它是否被打码（masked）；若没有，改成从受保护变量读取并重新验证。
2. 给测试仓库的 `main` 分支开启分支保护（要求 PR + 状态检查通过），然后尝试直接 push，确认被拒绝。
3. 故意在一条 fork 的 PR 里改 `.github/workflows`，观察你的主仓 CI 是否会自动用 fork 的改动执行——理解为什么"外部 PR 默认不该拿到仓库密钥"。
