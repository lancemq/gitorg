# Git 对象数据库

## 学完这篇你会掌握什么

- 理解 Git 为什么说自己是一个"内容寻址的对象数据库"，而不是文件版本列表
- 区分 blob、tree、commit、tag 四类对象各自的职责，以及它们如何靠哈希 ID 互链
- 理解为什么 blob 不保存文件名，以及内容复用为什么因此更自然
- 用对象模型解释日常命令：`git add` / `git commit` / `git branch` / `git checkout` 底层到底在动什么
- 建立"对象还在 ≠ 容易找到"的认知，为后续 reflog 与恢复内容打底


## 先想一个问题

你每天都在用 Git 命令，但偶尔会遇到一些 '奇怪' 的行为——比如明明没改文件却被提示有改动，或者 rebase 时突然多了预期之外的冲突。你想理解 Git 底层是怎么工作的。

## 一句话理解

Git 最底层不是“文件版本列表”，而是一个把内容写成对象、再用对象 ID 反向定位内容的数据库。

<MentalModelBox title="先别把 Git 想成网盘">
  <p>更稳的理解是：Git 先保存对象，再用分支、HEAD、tag 这些“名字”指向对象。你平时看到的是名字，Git 真正长期保存的是对象。</p>
</MentalModelBox>

## 为什么对象模型是第一层基础

很多 Git 现象只有放到对象模型里才说得通：

- 为什么一次 commit 会生成新的对象
- 为什么同样内容在不同分支上仍然可以复用
- 为什么 branch 创建几乎是瞬时的
- 为什么 reset 之后旧提交往往还没有真的消失

## 1. 什么叫内容寻址

Git 写入对象时，不是先给对象随便编号，而是先根据内容计算对象 ID。也就是说：

1. 内容先存在
2. ID 由内容决定
3. 之后 Git 再通过这个 ID 反向找到对象

这也是“content-addressable”最重要的含义。

## 2. 四类最常见对象

### blob

blob 只保存文件内容，不保存文件名，也不保存它在目录树中的位置。

### tree

tree 负责表达目录结构。它会记录目录下有哪些名字，以及这些名字指向哪个 blob 或哪个子 tree。

### commit

commit 用来固定一次项目状态。它通常会记录：

- 当前快照对应的 tree
- 父提交
- 作者和提交者信息
- 提交说明

### tag

tag 为某个对象提供更稳定、更可读的名字，常见于发布版本。

## 3. 为什么 blob 不保存文件名

这件事经常让人第一次接触 Git internals 时觉得反直觉。Git 把“内容”和“结构”分开保存：

- 文件内容放在 blob
- 文件名和目录位置放在 tree

好处是内容复用会更自然。只要内容一样，底层就能共享对象，而不必把“路径”和“内容”绑死。

## 4. 一次 commit 在对象层到底发生了什么

从对象数据库的视角看，一次提交大致是：

1. 根据暂存区内容写出 tree
2. 创建一个新的 commit 对象
3. 让 commit 指向这次 tree 和父提交
4. 再把当前分支引用移动到新提交

所以 commit 的本质不是“改写旧历史”，而是“新增对象，再移动名字”。

## 亲手拆开一次提交：用 `git cat-file` 看对象

光看概念还不够，最值钱的是亲眼看一次对象长什么样。Git 自带 `git cat-file` 可以把任意对象“打开”：

```bash
# 看 HEAD 最终指向什么类型的对象
git cat-file -t HEAD            # 通常输出 commit
git cat-file -t HEAD^{tree}     # 看它指向的 tree
git cat-file -p HEAD            # 打印 commit 对象的完整内容

# 顺着 tree 继续往里看
git cat-file -p $(git rev-parse HEAD^{tree})

# 再看某个 blob 的真实内容
git cat-file -p <blob-sha>
```

`-t` 打印类型（commit / tree / blob / tag），`-p` 按人类可读方式打印内容，`-s` 打印大小（字节数）。当你能顺着 `commit → tree → blob` 用自己的命令走一遍，对象模型就从“说法”变成了“你能验证的事实”。

## 5. 对象和工作区不是一回事

很多混乱来自把这两层混在一起。更稳的理解是：

- 工作区：你正在编辑的文件
- 暂存区：准备写入下一次快照的内容
- 对象库：已经被 Git 固化下来的对象

只有进入对象库之后，内容才真正成为 Git 历史的一部分。

## 6. 为什么对象模型能解释很多命令

### `git add`

它不是直接创建 commit，而是把当前内容朝下一次 tree 靠近。

### `git commit`

它会真正创建新的 tree 和 commit 对象。

### `git branch`

它通常不需要复制对象，只是新建一个指向已有提交的引用。

### `git checkout` / `git switch`

它们会让工作区去匹配另一个引用所指向的对象状态。

## 7. 对象“存在”不等于“容易找到”

这是理解恢复操作时最关键的一点。一个对象就算还在数据库里，只要没有分支、tag、reflog 之类的名字把它接住，你就会越来越难找到它。

所以很多恢复问题其实不是“对象没了”，而是“引用丢了”。

<TipBox title="这条理解对恢复特别重要">
  <p>很多“东西丢了”的 Git 事故，本质并不是对象被立刻删除，而是当前没有一个明显的引用还指向它。</p>
</TipBox>

## 常见误区

### Git 会为每个版本完整复制整个项目吗

不应该这样理解。Git 底层是对象模型，加上后面的 packfiles 压缩和复用机制，并不是简单粗暴地重复存整份目录。

### commit 只是写一段日志吗

不是。提交说明只是 commit 对象里的一部分元数据。真正关键的是它把 tree、父提交和作者信息固定了下来。

## 一个最实用的记忆方式

如果只记一件事，可以记住：

1. blob 保存内容
2. tree 保存结构
3. commit 保存一次快照与父子关系
4. branch 和 HEAD 只是指向这些对象的名字

后面理解 refs、历史图、rebase、reset 就会容易很多。

## 给你的练习

1. **亲眼看到对象**：在一个仓库里改一个文件并提交，`git cat-file -t HEAD` 确认它是 commit，`git cat-file -p HEAD` 看它指向的 tree，再 `git cat-file -p <tree-sha>` 看它指向的 blob，顺着哈希把"commit → tree → blob"这条链走通一遍。
2. **验证内容寻址**：把同一段内容放到两个不同路径的文件里分别提交，用 `git rev-parse :<path>` 确认它们最终指向同一个 blob 哈希——内容一样，哈希就一样。
3. **观察 branch 的轻量本质**：`git branch tmp` 后 `git cat-file -t tmp`，确认它只是一个指向已有 commit 的引用；再 `git log --oneline --all --graph` 看分支指针如何移动而不复制任何对象。
