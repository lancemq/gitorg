# 代码评审交接质量

## 学完这篇你会掌握什么

- 用"背景 / 范围 / 风险 / 验证"四要素写 PR 描述，让 reviewer 不用猜就能开审
- 知道哪些信息放 PR 描述、哪些放提交信息、哪些干脆自动化掉
- 用 `git range-diff` 管理 stacked PR 的层间差异，避免 reviewer 重复阅读

## 先想一个问题

reviewer 打开一个 PR，看到标题 "update logic"，描述栏空白。他现在需要：翻 issue 找背景、逐文件猜改动意图、私聊作者问"这个函数为什么这么写"。十五分钟过去了，评审还没真正开始。

这个成本几乎完全由作者侧决定：**交接质量高的 PR，reviewer 十分钟能给出有效反馈；交接质量差的 PR，三轮往返都未必对齐**。评审慢，多数时候不是 reviewer 慢，是 handoff 缺信息。

## 一句话理解

评审交接 = 把 reviewer 需要的判断依据前置给齐，让对方的时间花在判断上，而不是补全上下文上。

## 四要素 PR 描述模板

直接抄进团队 Wiki 用：

```markdown
## 背景（Why）
<一两句话：哪个需求/bug 导致这次改动，链接 issue>

## 改动范围（What）
- <关键变更点 1>
- <关键变更点 2>
- 明确不改什么：<边界说明，防止 reviewer 提范围外建议>

## 风险与影响面（Risk）
- <可能受影响的模块/接口>
- <最坏情况与已做的防护>

## 如何验证（How tested）
- 单测：<新增/修改了哪些用例>
- 手工：<在哪个环境做了什么操作，看到什么结果>
```

四要素的判断标准：reviewer 读完描述后，**不看代码也能复述出"这个 PR 在干嘛、为什么这么干、改坏了会怎样"**。做不到，就是还缺信息。

## 信息该放在哪一层

| 信息 | 放哪 | 原因 |
| --- | --- | --- |
| 为什么改、不改什么 | PR 描述 | 评审决策的依据 |
| 这一个提交干了什么 | commit message | `git log` 单独可读 |
| "检查项 A 通过" | CI | 机器可判定的别用人眼 |
| 逐行实现说明 | 代码注释 | 跟着代码走，别写进描述 |

常见反模式是把实现细节堆进 PR 描述（"我在第 42 行加了个 if"）——reviewer 会看到 diff，描述里只需要讲 diff 看不出来的东西：意图、取舍、风险。

## Stacked PR 的交接要点

分层 PR 的额外风险是 reviewer 重复阅读已审过的层。两个动作解决：

**每层描述只讲"本层新增差异"**，开头一句话写明依赖："基于 #123（已合并/待合并），本层在其之上新增了缓存逻辑"。

**层间变动用 `git range-diff` 贴出对比**。上层 PR 因下层 rebase 而变化时：

```bash
# 对比上层 PR 在下层 rebase 前后的提交差异
git range-diff origin/main...pr-branch-old origin/main...pr-branch-new
```

输出会逐提交标注 unchanged / modified / added，reviewer 只需要看 modified 的部分。

<WarningBox title="别把 reviewer 当成需求背景探测器">
  如果上下文全靠 reviewer 自己翻 issue、问产品、猜意图，评审必然变慢且判断质量波动大。"我着急先合了再补描述"的 PR，大概率在评审里把着急的时间加倍赔回去。
</WarningBox>
