# API 版本变更工作流

## 推荐步骤

### 1. 明确哪些变更属于破坏性

例如字段语义变化、默认行为变化、认证方式变化。

### 2. 发布并行版本

在迁移窗口内同时支持旧版和新版接口。

### 3. 公布迁移文档与截止日期

至少包括差异说明、示例请求、错误码变更和时间计划。

### 4. 监控客户端迁移进度

按调用量、错误率和客户端版本维度跟踪。

### 5. 到期下线旧版本

下线前应完成通知、预演和应急回开方案。

<WarningBox title="没有迁移窗口的破坏性升级会直接外溢为生产事故">
  即使接口设计正确，如果客户端升级节奏不可控，强制切换仍会触发大面积失败。版本治理必须包含沟通和窗口管理。
</WarningBox>

## 对应的 Git 操作序列

版本分支与下线收尾，落到 Git 上就是这几条命令：

```bash
# 从主干切出旧版本的维护分支，迁移窗口内两版并行
git switch -c api/v1-maintenance origin/main
git push origin api/v1-maintenance

# 新版本开发继续在 main 上走常规 MR

# 迁移截止、监控归零后，给旧版本打最后一个维护 tag 再归档分支
git tag -a v1.9.9 api/v1-maintenance -m "final v1 maintenance release"
git push origin v1.9.9
git push origin --delete api/v1-maintenance
```

要点：维护分支只收修复类 cherry-pick，不收功能；下线分支前打 tag，保证历史随时可查。

## 常见误区

### 误区 1：版本号有了就算治理完成

没有迁移计划和观测数据，版本号只是标签。

### 误区 2：所有客户端都能同步升级

真实环境中客户端升级速度差异很大。

### 误区 3：旧版本永不下线

会造成长期维护负担与安全风险叠加。

<PracticeBox title="为一次 API 破坏性变更写迁移计划">
  1. 列出破坏性差异点。
  2. 设定迁移窗口起止日期。
  3. 定义迁移进度监控看板字段。
  4. 写明旧版下线与紧急回开策略。
</PracticeBox>
