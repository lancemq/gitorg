# Canary 发布工作流

## 适用场景

- 新版本影响核心路径，风险不适合全量一次性释放
- 团队具备灰度路由和实时监控能力
- 需要在真实线上环境验证性能和兼容性

## 推荐步骤

### 1. 定义 canary 通过条件

至少包括：错误率、延迟、关键业务指标。

### 2. 部署小流量版本

例如先从 1% 或单可用区开始。

### 3. 观察窗口内评估指标

设定固定观察时间，避免“刚上线就马上全量”。

### 4. 逐级放量

1% → 5% → 20% → 50% → 100%，每一步都必须重新评估。

### 5. 触发阈值时立即止损

优先停止放量，必要时回滚版本或关功能开关。

<WarningBox title="没有阈值定义的 canary 只是“慢速全量”">
  如果团队没有明确“何时通过、何时回滚”的门槛，金丝雀发布无法发挥风险控制作用。
</WarningBox>

## 对应的 Git 操作序列

金丝雀版本的分支与标签操作：

```bash
# 从 release 分支切出 canary 分支，部署小流量环境
git switch -c release/2.5.0-canary release/2.5.0
git push origin release/2.5.0-canary

# 每一级放量通过后，若需带修复进入下一级，用 cherry-pick 同步
git switch release/2.5.0-canary
git cherry-pick <fix-commit>

# 全量通过后，把 canary 分支快进合并回 release 分支并打正式 tag
git switch release/2.5.0
git merge --ff-only release/2.5.0-canary
git tag -a v2.5.0 -m "canary validated release"
git push origin release/2.5.0 v2.5.0
```

要点：canary 分支上的改动用 cherry-pick 进来而不是直接提交，保证与 release 分支的差异始终只有"待验证的修复"。

## 常见误区

### 误区 1：只看技术指标，不看业务指标

技术指标正常不代表转化路径正常。

### 误区 2：观察窗口过短

很多问题会在峰值流量或异步任务阶段才暴露。

### 误区 3：canary 和 feature flag 职责混淆

canary 控制版本流量，flag 控制功能开关，两者可配合但不等价。

<PracticeBox title="设计一次 canary 放量门禁">
  1. 定义 3 个核心技术指标与阈值。
  2. 定义 2 个关键业务指标与阈值。
  3. 定义每个放量阶段最短观察时长。
  4. 指定谁有权执行停止放量。
</PracticeBox>
