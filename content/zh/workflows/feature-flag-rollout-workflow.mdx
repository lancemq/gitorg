# Feature Flag 渐进发布工作流

## 适用场景

- 新功能影响核心流程，风险不可一次性全量
- 需要 A/B 或分群发布能力
- 希望在不频繁发版的前提下调整开放策略

## 推荐流程

### 1. 先实现可关闭路径

功能代码必须在 flag 关闭时保持旧行为完整可用。

### 2. 合并到主线并保持默认关闭

```bash
git switch -c feature/new-checkout-flow
git commit -m "add new checkout flow behind flag"
```

### 3. 从内部用户开始小流量灰度

逐步从 1% → 5% → 20% → 50% → 100%，每一步观察核心指标。

### 4. flag 的三种技术形态

```bash
# 1. 配置中心/远端开关（LaunchDarkly、自建 admin API）——改配置不发版，灰度首选
curl -X POST https://flags.internal/api/toggle   -d '{"flag":"new-checkout-flow","percent":5}'

# 2. 环境变量/配置文件——改了要重启，适合粗粒度（整站级）
FEATURE_NEW_CHECKOUT=off

# 3. 代码内常量——改了要走发版，只适合「合并但暂不启用」的短周期场景
const NEW_CHECKOUT_ENABLED = false;
```

形态决定回滚速度：线上事故时，形态 1 秒级恢复、形态 2 分钟级、形态 3 只能走完整回滚流程。核心路径的灰度至少要做到形态 1 或 2。

### 5. 异常时优先关闭旗标

如果出现指标恶化，先关旗并恢复旧路径，再决定是否回滚代码。

### 6. 稳定后删除旗标与死代码

长期遗留 flag 会增加代码复杂度，应设定清理时限。

<WarningBox title="没有观测能力的灰度，等于盲飞">
  如果没有延迟、错误率、转化等关键指标，渐进放量只是“慢一点冒险”。放量前先确认指标面板和告警阈值。
</WarningBox>

## 常见误区

### 误区 1：一个 flag 控制太多行为

职责不清会导致回滚时影响面不可预测。

### 误区 2：异常后一边关旗一边继续推新代码

应先止损，再恢复排查节奏。

### 误区 3：稳定后不清理 flag

最终会形成难以维护的“配置债务 + 分支逻辑债务”。

<PracticeBox title="为下个高风险功能写一份放量计划">
  1. 定义默认关闭状态下的行为。
  2. 定义 4 个放量阶段和每阶段通过条件。
  3. 写清“关旗触发阈值”和执行责任人。
  4. 设定 flag 下线日期。
</PracticeBox>
