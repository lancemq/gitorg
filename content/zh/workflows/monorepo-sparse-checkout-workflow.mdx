# monorepo 场景下的稀疏检出与多工作树协作

## 学完这篇你会掌握什么

- 在 monorepo 场景里，用 sparse-checkout 和 worktree 限定工作范围，降低上下文负担并支持并行任务。
- `sparse-checkout`：只拉起当前需要的目录
- `worktree`：为并行任务开多个独立工作副本

你只改前端应用，但仓库里还有后端、脚本、基础设施和大量共享包。  
如果每次都把整棵树都拉起来，成本会很高。

## 一条可执行流程

```bash
# 1. clone 时就声明只要部分目录（cone 模式，最推荐）
git clone --sparse --filter=blob:none git@github.com:org/monorepo.git
cd monorepo

# 2. 已有仓库切 cone 模式
git sparse-checkout set --cone

# 3. 声明你要的目录
git sparse-checkout set services/payment packages/ui

# 4. 加目录 / 看当前清单
git sparse-checkout add services/inventory
git sparse-checkout list

# 5. 不想用了，恢复全量
git sparse-checkout disable
```

`--filter=blob:none` 与 sparse-checkout 是配套的：前者让 clone 不下载无关 blob（省网络与存储），后者让工作区只检出声明的目录（省磁盘与 IDE 索引时间）。只加后者不加前者，对象还是会全量下载。

```bash
git sparse-checkout init --cone
git sparse-checkout set apps/web packages/ui
git worktree add ../repo-hotfix hotfix/login-fix
```

这样你可以：

- 在当前工作树处理主任务
- 在另一个 worktree 里处理热修
- 同时让当前工作区范围保持更小

## 和 submodule 的边界

如果仓库本身就是 monorepo，优先考虑 sparse-checkout / worktree。  
如果你管理的是独立仓库依赖关系，才更可能落到 submodule。

## 一个原则

在大型仓库里，Git 工作流优化的关键不只是命令更高级，而是把“我现在真正要改的范围”压缩到足够清楚。
