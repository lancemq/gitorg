# git status 教程

`git status` 是唯一一条「随时可以跑、永远不改变任何东西」的命令。它的价值不在于告诉你改了什么，而在于**在你执行有风险的动作之前，确认你以为的状态就是真实状态**。

但它有两种形态：给人看的和给脚本看的。混用是常见错误来源。

## XY 两列：先分清索引和工作区

```bash
git status
```

```
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   src/app.ts

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   src/config.ts

Untracked files:
        notes.md
```

`--short` 把它压成两列字母，信息密度高得多：

```bash
git status --short
# M  src/app.ts        ← 第一列 M：已暂存（索引里有改动）
#  M src/config.ts     ← 第二列 M：工作区改了，还没 add
# ?? notes.md          ← 未跟踪
```

**左列（X）= 索引相对 HEAD 的差异，右列（Y）= 工作区相对索引的差异。**

| 组合 | 含义 | 下一步 |
|------|------|--------|
| `M ` | 已暂存，工作区干净 | 可以 commit |
| ` M` | 未暂存 | 需要 `git add` |
| `MM` | 暂存后又改了 | 两处都有改动，`add` 会覆盖暂存版本 |
| `A ` | 新文件已暂存 | 可以 commit |
| `??` | 未跟踪 | `git add` 才会纳入 |
| `!!` | 被忽略（需 `--ignored`） | — |
| `R ` | 重命名 | 显示为 `old -> new` |
| `UU` | 冲突未解决 | 必须先解决 |

`MM` 是最容易看错的一种：文件被 `add` 过，之后又改了。此时 `git diff` 显示工作区的那部分改动，`git diff --staged` 显示已暂存的部分，`git diff HEAD` 才是全部。

## ahead / behind 从哪来

```
Your branch is ahead of 'origin/main' by 2 commits.
```

这是在比较本地 `main` 与 `refs/remotes/origin/main`。**它反映的是上次 fetch 之后的远端状态**，不代表服务器现在的样子。看到 `behind 3` 时，先 `git fetch` 再看一次，数字可能变。

紧凑版：

```bash
git status -sb
# ## main...origin/main [ahead 2, behind 3]
#  M src/config.ts
```

`-b` 加分支行，`-s` 用 short 格式，`-sb` 是最适合日常盯着的组合。三个点 `...` 表示两边都有各自的提交；如果显示成 `## main` 没有上游，说明这个分支还没设置 upstream。

## 脚本里必须用 --porcelain

默认输出会跟着配置变（`status.short`、`status.branch`、`color.status`），而且提示语会随语言环境翻译。任何解析它的脚本都会在别人的机器上坏掉。

```bash
git status --porcelain        # v1，稳定但字段少
git status --porcelain=v2     # v2，带分支信息，推荐
```

`--porcelain` 自动关闭颜色、关闭相对路径、固定为 short 格式，并且不随 `status.short` 变化。v2 还能直接读到 ahead/behind：

```bash
git status --porcelain=v2 --branch
# # branch.oid 3f2a91c8...
# # branch.head main
# # branch.upstream origin/main
# # branch.ab +2 -3
# 1 .M N... 100644 100644 100644 8b1d44e 8b1d44e src/config.ts
```

`branch.ab +2 -3` 就是 ahead 2 / behind 3，不需要再解析自然语言。

路径可能含空格或中文时，加 `-z` 用 NUL 分隔：

```bash
git status --porcelain=v2 -z | tr '\0' '\n'
```

`-z` 还会关掉路径的引号转义，中文名会原样输出，而不是 `"\346\226\207..."` 这种八进制形式。

## 看被忽略的文件

默认不显示，但排查「为什么这个文件没被跟踪」时需要它：

```bash
git status --ignored
#  M src/app.ts
# !! node_modules/
# !! dist/
# !! .env
```

`--ignored=matching` 只显示匹配的条目本身，`--ignored=traditional` 会显示整个被忽略的目录。规则没生效时，用这条命令配合 `git check-ignore -v <path>` 能直接看到是哪个 `.gitignore` 的哪一行在起作用。

## 重命名的显示条件

```bash
git mv old.ts new.ts
git status --short
# R  old.ts -> new.ts
```

这里的 `R` 是**索引层面**的记录，`git mv` 会把它标记为重命名。但如果用 `mv` + `git add -A`，`status` 也能推断出来——前提是内容相似度足够，否则会显示成一删一增：

```
D  old.ts
?? new.ts
```

## 缩减输出的配置

```bash
# 默认就用 short 格式
git config --global status.short true

# 默认带分支行
git config --global status.branch true

# 不显示未跟踪文件（大仓库里 untracked 可能几千个）
git config --global status.showUntrackedFiles no

# 但保留某个目录的显示
git status --untracked-files=normal
```

`showUntrackedFiles=no` 在大仓库里能把 `status` 从几秒降到瞬时，代价是「新建了文件却忘了 add」这类问题要靠别的办法发现。用 `normal`（默认）比 `all` 更克制：`all` 会展开未跟踪目录里的每个文件。

## 排序与分列

```bash
git status --column            # 按列排版，宽屏下更好读
git status --no-column
```

`status.showUntrackedFiles` 是全局的，`--column` 只影响显示布局。终端宽度变化时列数会重排，所以它不适合管道输出。

## 一条实践规则

在任何「可能丢东西」的命令之前跑一次：

```bash
git status --short
```

需要它的场合：

- `git reset --hard`（未提交改动直接消失）
- `git checkout -- .` / `git restore .`（同上）
- `git clean -fd`（未跟踪文件永久删除）
- `git rebase` / `git merge`（冲突时的工作区状态会被覆盖）
- `git pull`（会尝试合并，先知道自己在什么状态）

一个具体例子：`git clean -fd` 删的是未跟踪文件，而这些文件**不在 Git 里，没有任何恢复手段**。执行前 `git status --short | grep '^??'` 看一眼，比事后找磁盘恢复工具便宜得多。

## 常见误解

**「status 干净就等于可以安全操作」**。它只反映工作区和索引，不反映你已经 rebase 过、或者本地有未推送的提交。ahead 的数字也是本地认知。

**「status 慢是 Git 的问题」**。多数情况是未跟踪文件太多，或者文件系统监控（如 `core.fsmonitor`）没配好。`git status --porcelain` 加计时能看到差异。
