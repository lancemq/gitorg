# git-am 教程

`git am` 不是「应用一个补丁文件」，而是「**执行一批补丁**」。它按顺序把邮件格式的补丁逐个变成提交，中途任何一封失败都会暂停整个队列，等你的决定。

这条设计决定了它的所有行为：为什么有 `--continue`、为什么有队列状态、为什么 `--abort` 会一次性回退全部。

## 和 git apply 的根本区别

```bash
git am 0001-fix-login.patch    # 生成提交，保留原作者与提交信息
git apply 0001-fix-login.patch # 只改文件，不生成提交
```

`git am` 解析的是邮件格式：`From <sha>` 分隔线、`From:` 作者、`Date:` 时间、`Subject:` 作为提交标题、分隔线之后的正文作为提交说明。所以它能还原「这个改动是谁、什么时候、为什么做的」。

如果补丁里没有这些头信息（纯 diff），`git am` 会失败：

```
Patch is empty.  Was it split wrong?
```

这时该用 `git apply`。

## 基本流程

```bash
# 单个补丁
git am 0001-fix.patch

# 一批补丁（按文件名排序，编号顺序即应用顺序）
git am *.patch

# 从邮件导出的 mbox（一封文件里多封邮件）
git am mailbox.mbox

# 从标准输入
curl -s https://lore.kernel.org/patch/12345/raw | git am -
```

应用成功后，每个补丁产生一个提交，作者保持原样，committer 是你。

## 中途冲突时

补丁队列跑到一半失败，Git 会停下来并保留整个队列状态：

```
Applying: fix: correct timeout handling
error: patch failed: src/client.ts:88
error: src/client.ts: patch does not apply
Patch failed at 0003-fix-timeout
hint: Use 'git am --show-current-patch=diff' to see the failed patch
```

三个选择，语义差别很大：

```bash
# 1. 手工解决冲突后继续（必须先 git add）
git add src/client.ts
git am --continue

# 2. 放弃当前这一封，继续下一封
git am --skip

# 3. 放弃整个队列，回到 am 开始前的状态
git am --abort
```

`--skip` 的代价要说清：被跳过的这个补丁**不会出现在历史里**。后续补丁如果依赖它，会继续失败。连续 skip 通常意味着基线选错了，应该 `--abort` 后换基线重来，而不是硬着头皮跳。

先看失败的补丁长什么样：

```bash
git am --show-current-patch=diff    # 只看 diff
git am --show-current-patch=raw     # 完整邮件原文（含提交信息）
```

## --3way：让基线漂移的补丁也能打上

补丁往往基于旧版本生成，直接应用会因上下文不匹配失败。`--3way` 让 Git 用补丁里记录的 blob 做三方合并：

```bash
git am --3way *.patch
```

想让它成为默认行为（强烈建议在补丁工作流里开启）：

```bash
git config --global am.threeWay true
```

`--3way` 失败时不是直接中止，而是留下冲突标记让你解决，解决后同样 `git add` + `--continue`。相比「完全打不上」，这通常省下大量手工对齐的时间。

## -i：逐个确认

批量导入来自邮件列表的补丁时，你可能只想选择性应用：

```bash
git am -i mailbox.mbox
```

每封补丁都会暂停并询问，可以选择应用、跳过或编辑提交信息。适合「这批补丁里有些与当前分支无关」的场景。

## 提交信息处理

```bash
git am --signoff *.patch      # 追加 Signed-off-by: 你
git am --keep-cr *.patch      # 保留 CRLF 行尾（Windows 来源的补丁）
git am --committer-date-is-author-date *.patch  # 用作者时间当提交时间
```

`--keep-cr` 在处理从 Windows 邮件客户端转发的补丁时几乎必需，否则行尾会被规范化，导致后续每个补丁都冲突。

## 队列状态放在哪

`git am` 复用 rebase 的 apply 后端，状态在 `.git/rebase-apply/`：

```bash
ls .git/rebase-apply/
# 0001  0002  0003  next  last  patch  …
```

| 文件 | 含义 |
|------|------|
| `next` / `last` | 当前处理到第几个补丁、总共几个 |
| `patch` | 正在应用的那一封原文 |
| `0001`、`0002`… | 已应用的补丁副本 |

知道这个目录存在有两个用处：一是理解 `--abort` 为什么能一次性回退（它删掉这个目录并把 HEAD 恢复），二是队列卡死时能确认还有几封没处理。

## 常见失败与对策

**补丁序列顺序错了**。`git am *.patch` 依赖文件名排序，`0001-`、`0002-` 这种前缀是有意义的。如果文件名不带序号，先排序再传给 `git am`：

```bash
ls -1 *.patch | sort -V | xargs git am
```

**空补丁导致中断**。某些补丁在目标分支上已经应用过，内容为空：

```bash
git am --empty=skip *.patch    # 跳过空补丁
git am --empty=keep *.patch    # 仍生成一个空提交（保留提交信息）
```

**应用后想撤销**。`--abort` 只在队列未结束时可用。已经全部应用完才发现不对，只能从 reflog 回退：

```bash
git reflog
git reset --hard HEAD@{n}    # n = am 开始前的位置
```

## 稳定使用的顺序

```bash
# 1. 干净起点
git switch -c apply/patches main
git status --short          # 必须为空

# 2. 单个补丁可以先干跑（git am 本身没有 --check，用 apply 代替）
git apply --check 0001-fix.patch

# 3. 真正应用
git am --3way *.patch

# 4. 检查结果：提交数、作者是否保留
git log --oneline -5
git log -1 --format='%an <%ae>'
```

`git am` 没有全局 dry-run 选项，所以整批「能不能过」只能在临时分支上真跑一遍。这也是为什么第 1 步建分支、第 3 步失败时用 `--abort` 回退值得坚持——代价只是重跑一次，而不是在主干上收拾残局。

<WarningBox title="先确认补丁基线再 am">
  基线漂移会让补丁序列在中途大量冲突，处理成本远高于先同步一次历史。在临时分支上先跑一遍，确认整批能过再正式应用。
</WarningBox>
