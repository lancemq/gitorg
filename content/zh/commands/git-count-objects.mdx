# git-count-objects 教程

## 先想一个问题

`du -sh .git` 涨到几个 G，你想知道这些字节花在哪。`git count-objects -v` 把对象库拆成松散对象、pack 文件、garbage、以及可回收空间几项。读懂这几行，才能判断下一步是该 `git gc`，还是该去查那个一直变大的文件。

## 读懂 -v 的每一行

```bash
$ git count-objects -v
count: 17                  # 松散对象个数
size: 2136                 # 松散对象占用（KB，磁盘计）
in-pack: 48219             # 已打进 pack 的对象总数
packs: 3                   # pack 文件个数
size-pack: 15234           # pack 总占用（KB）—— 仓库体积的主力
prune-packable: 0          # 已被打包但仍留着松散副本的对象
garbage: 4                 # .git 里既非对象也非 pack 的文件数
size-garbage: 12           # garbage 占用（KB）
```

判断顺序：`count` 大（比如几千上万）说明该 gc 了——Git 自动 gc 的触发线是约 6700 个松散对象（`gc.auto` 默认值），日常 rebase/am 频繁的仓库很容易攒到。`size-pack` 才是仓库真实体积；它大而提交不多时，问题多半在二进制大文件，下一步用 `git rev-list --objects --all` 配合 `git cat-file --batch-check` 定位具体 blob。

## 和 gc.auto 联动

```bash
git config gc.auto                 # 6700（默认），松散对象超过这个数触发自动打包
git config gc.autoPackLimit        # 50，pack 文件超过这个数触发自动合并 pack
```

`git count-objects -v` 里的 `count` 就是和 `gc.auto` 比对的那个数。CI 机器上经常出现「从不自动 gc」——因为 `git gc --auto` 只在部分命令里被触发，且前台交互式的 `git commit` 在后台执行它时若耗时过长会被跳过。定期任务里显式跑 `git gc --auto`（或全量 `git gc`）更可靠。

## 实际排障示例

**例一：rebase 一天后变卡**

```
count: 8421    ← 超过 6700
size-pack: 15234
```

诊断：大量 rebase/am 留下松散对象。处理：`git gc` 后 `count` 归个位数，`size-pack` 基本不变（这些对象本来就该进 pack）。

**例二：clone 后体积远超同事**

```
garbage: 2107
size-garbage: 358123   ← 350MB 垃圾
```

诊断：`.git` 里有中断操作留下的临时文件（常见于 gc 被强杀、`git clone --depth` 失败重试）。处理：先 `git prune` 无效时，检查 `.git/objects/pack/tmp_*` 和 `.git/gc.log`；`garbage` 计数高时 Git 会拒绝自动 gc 并把原因写进 `gc.log`，看那个文件比猜快得多。

## 边界

- 纯只读，不改仓库任何状态。
- `size`/`size-pack` 单位是**磁盘占用（KB）**，不是对象内容字节数——压缩和文件系统块大小都会影响，别拿它和 `du` 之外的数字硬对。
- 它只回答「多少、多大」，不回答「谁大」；定位大对象要用 `git rev-list --objects --all` 加 `git cat-file --batch-check`（见 git-cat-file 教程）。
- `prune-packable` 长期不为 0 无需处理，下次 gc 会清掉。
