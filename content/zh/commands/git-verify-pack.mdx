# git-verify-pack 教程

## 先想一个问题

pack 文件是 Git 压缩对象后的产物，`.idx` 是它的索引。`git verify-pack -v .git/objects/pack/*.idx` 会列出 pack 里每个对象的类型、原始大小、以及在 pack 内占用的字节数。查"仓库为什么这么大"时，这是唯一能看到压缩后真实体积的地方。

## 读懂 -v 的输出

```bash
$ git verify-pack -v .git/objects/pack/pack-*.idx | head -6
1a2b3c4 commit 231 142 12
5d6e7f8 blob   1204896 8931 154      # SHA 类型 原始大小 pack内大小 偏移
9a8b7c6 blob   511    318 9085 1 5d6e7f8   ← 末尾两个数：delta 基准的深度和 hash
...
non delta: 23112 objects
chain length = 1: 4521 objects
chain length = 2: 893 objects
...
```

每行五列是普通对象：SHA、类型、**原始大小**、**压缩后在 pack 里的大小**、偏移。七列是 delta 对象，多出的两列是 delta 链深度和基准对象。对比第 3、4 列就能看出压缩收益：上面那个 1.2MB 的 blob 压到 8.9KB，说明它和链上某个基准对象高度相似。

结尾的 `chain length` 分布是存储健康度信号：深度 1-2 占多数是正常的；大量深度 40+ 的对象说明 delta 链过长，读取时 要沿链解压多次，`git gc`（`pack.depth` 默认 50，`pack.window` 默认 10）重建后通常会显著缩短。

## 三个实战组合

**找 pack 里最大的对象**（比 count-objects 精确到单个 blob）：

```bash
git verify-pack -v .git/objects/pack/pack-*.idx \
| sort -k3 -n -r | head -10 \
| awk '{print $3, $1}' \
| while read size hash; do
    echo -n "$size bytes: "
    git rev-list --objects --all | grep "$hash" | cut -d' ' -f2
  done
```

**校验收到的 pack 是否完整**（收到 bundle 或手工拷贝的 pack 后）：

```bash
git verify-pack -v pack-xxx.idx   # 只列对象不报错 = 结构完整
```

注意：它校验的是 pack 内部结构和 `.idx` 的一致性，**不校验对象是否可达**——一个损坏引用指向的孤儿 pack 它照样说没问题，可达性要用 `git fsck`。

**统计 delta 压缩效率**：

```bash
git verify-pack -v pack-*.idx | grep -c "chain length" -A0
git verify-pack -v pack-*.idx | grep "non delta"   # 未压缩对象数
```

non delta 占比高（比如超过一半）说明仓库里独立二进制多，delta 帮不上忙——这类仓库该上 LFS 而不是调 pack 参数。

## 边界与坑

- 传入的是 `.idx` 不是 `.pack`；通配 `pack-*.idx` 一次跑全部。
- **慢**：要解压整条 delta 链，几百 MB 的 pack 要跑几十秒到几分钟。它是诊断工具，别放进 CI 常规流程。
- 只读，不会修改 pack 或仓库状态。
- 找「谁在占空间」之后想清理，是 `git filter-repo` 的事；本命令只负责定位，不动历史。
