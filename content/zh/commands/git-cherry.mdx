# git-cherry 教程

## 先想一个问题

`git cherry <upstream> <head>` 回答一个很具体的问题：这个分支上哪些提交，上游已经有了等价改动？它靠 patch-id 判断，所以能识别"cherry-pick 过但 hash 已经变了"的情况——这正是 `git log --left-right` 看不出来的部分。

## 读懂 +/− 输出

```bash
$ git cherry origin/main feature/login
+ 3a91f2c add login validation
- 8d2e4b1 fix navbar overlap      ← 已被上游吸收（patch-id 相同）
+ c7f1a03 add remember-me token   ← 上游还没有
```

`-` 开头的提交内容已存在于上游（哪怕 hash 不同），`+` 开头的是真正待合并的。全部 `-` 说明这个分支可以安全删除。加 `-v` 显示提交标题，不用逐个 hash 去 log：

```bash
git cherry -v origin/main feature/login
```

## 典型场景：发布分支回写判断

维护 `release/2.1` 时，hotfix 先落在 release 分支，再 cherry-pick 回 main。一个月后问「哪些修复还没回 main」：

```bash
git cherry main release/2.1
```

输出全是 `-` 就是都回去了；还挂着 `+` 的，就是 cherry-pick 时被冲突处理改了内容、patch-id 对不上，需要人工确认。

## patch-id 的边界

- **判断依据是补丁内容**：作者、日期、提交信息都可以不同，只要 diff 一样就算等价。
- **冲突解决会破坏匹配**。cherry-pick 时手工改过的提交，patch-id 变了，会显示 `+`——这是"显示为未吸收但实际内容已在"的主要来源，不能盲信输出，`+` 的条目要抽查。
- **上下文行不同也算不同**。上游在相邻代码插过行后，同一个逻辑修复的 diff 上下文变了，patch-id 就对不上。这时 `git cherry` 会高估剩余工作量。
- 只比较 `<upstream>..<head>` 范围内的提交；`<head>` 省略时是当前分支。

`git cherry` 完全只读，不移动引用、不建对象。需要真正执行"把没吸收的搬过去"，那是 `git rebase --onto` 或 `git cherry-pick` 的事。
