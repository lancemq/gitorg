# git-fsck 教程

## 先想一个问题

仓库突然报 `fatal: object ... is corrupt`，或者 clone 之后 `git log` 走到某处就断。`git fsck` 回答的是"对象库到底还完整吗"。它只读、随时可跑，但输出里的 `dangling`（悬空，通常无害）和 `missing`（缺失，需要处理）是完全不同的两件事。

## 读懂四类输出

```bash
$ git fsck --full
Checking object directories: 100% (256/256), done.
dangling commit 3a91f2c8...     ← 没有引用指向它，但对象完好
missing blob 5d6e7f8a...        ← 引用存在，对象内容丢了（严重）
broken link from  tree 9a8b7c6  ← 树里记录的子对象不存在（严重）
error: HEAD: invalid sha1 pointer 1a2b3c4   ← 引用本身坏了（严重）
```

判断规则：**dangling 结尾的行不用慌**——那只是「没人引用但还在」的对象，往往是一次 reset/amend 留下的旧提交，甚至是救援的机会；`missing`、`broken link`、`error` 才是损坏，需要处理。

## 找回悬空提交：fsck 的另一面

`git reset --hard` 丢了的提交，reflog 也查不到时（比如 reflog 过期被清），fsck 是最后的绳索：

```bash
git fsck --full --unreachable --no-reflogs
# unreachable commit 3a91f2c8...
git show 3a91f2c8                 # 先看内容对不对
git switch -c rescue/lost-work 3a91f2c8   # 确认后建分支接住它
```

悬空对象会在 gc 后被真正删除（默认 2 周宽限，`gc.pruneExpire` 可调），所以发现丢数据要尽快救。

## 损坏的处理路径

- **单个 blob 缺失**：能从远端补——`git fetch` 拉全量后 `git reset --hard origin/main`；没有远端就只剩备份一条路。
- **pack 损坏**：报 pack 相关错误时，先 `git verify-pack` 定位坏 pack，删掉它再从远端重新 fetch。
- **整个 .git 报大量错误**：别反复跑 fsck 或 gc，立即停手，把整个目录拷一份再操作；然后在工作区文件还在的前提下 `git init` 重建对象库，靠 `git add` 把现状重新收编。
- `--lost-found` 会把悬空对象写成 `.git/lost-found/` 下的文件，比记 hash 直观，适合损坏现场保存证据。

## 边界

- 纯只读，`--lost-found` 也只是写新文件、不动已有对象。
- 大仓库 `--full` 要解压校验所有对象，几十万提交的仓库可能跑几分钟，放后台跑。
- 它不检查工作区文件、不检查远端仓库，只看本仓库 `.git` 里的对象库。
- `--no-dangling` 可屏蔽悬空对象输出，日常完整性检查用它能少一半噪声。
