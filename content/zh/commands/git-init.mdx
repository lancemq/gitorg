# git init 教程

`git init` 做的事比它看起来多：它不只创建 `.git` 目录，还决定了这个仓库的对象格式、初始分支名、共享权限，以及后续所有命令的默认行为。

## 最小用法

```bash
mkdir my-project && cd my-project
git init
```

输出会告诉你建了什么：

```
Initialized empty Git repository in /path/my-project/.git/
```

此时 `git status` 会显示 `No commits yet`，所有文件都是未跟踪状态——**init 不产生任何提交**，历史的第一条要你手动 `git add` + `git commit` 才会出现。

## 重复执行是安全的

这是最常被误解的一点：在已有仓库里再跑一次 `git init`，不会清空任何东西。

```bash
git init
# Reinitialized existing Git repository in /path/my-project/.git/
```

它的真实语义是「确保这个目录是一个仓库，并补齐缺失的元数据结构」。已有对象、引用、配置全部保留。所以「误在项目里又 init 了一次」不需要抢救。

## 指定初始分支名

Git 2.28 起可以直接指定，不再依赖版本默认值：

```bash
git init -b main
```

想让它成为所有新仓库的默认：

```bash
git config --global init.defaultBranch main
```

不设的话，Git 会按编译时的默认值走（常见是 `master`），并在每次 init 时打印一条 hint 提示你配置——这条提示不是错误。

## --bare：没有工作区的仓库

```bash
git init --bare repo.git
```

区别不在名字，在结构：

| | 普通仓库 | `--bare` 仓库 |
|---|---|---|
| 结构 | 工作区 + `.git/` 子目录 | 目录本身就是仓库内容 |
| `HEAD`、`objects/`、`refs/` | 在 `.git/` 里 | 直接在根目录 |
| 能否直接编辑文件 | 能 | 不能，没有工作区 |
| 典型用途 | 日常开发 | 服务端、CI 的中央仓库 |

在 bare 仓库里执行 `git status` 会说这不是工作区。这也是为什么服务端 hook 里不能用 `git diff`——没有工作区可比，必须用 `git diff <old> <new>` 或 `git cat-file`。

```bash
# 本地建一个「远端」，常用于测试推送行为
git init --bare /tmp/remote.git
git remote add origin /tmp/remote.git
git push -u origin main
```

## --shared：多人共用一台机器上的仓库

团队在共享服务器上共用一个仓库目录时，默认权限会让别人无法写入。`--shared` 调整的是 `core.sharedRepository`：

```bash
git init --shared=group repo.git    # 同组可读写
git init --shared=all repo.git      # 所有人可读写
git init --shared=0660 repo.git     # 直接指定权限位
```

它同时会把新建对象和目录的权限设为组可写，避免「A 推上去的对象 B 无法读取」这类问题。事后补救也能改，但要连带修 `objects/` 下已有文件的权限：

```bash
git config core.sharedRepository group
chmod -R g+rwX .
```

## --template：控制新仓库里预置什么

`git init` 会把模板目录（默认 `/usr/share/git-core/templates`）里的内容复制进新仓库的 `.git`。最实用的用法是带上团队的标准 hook：

```bash
mkdir -p /opt/git-templates/hooks
cp team-commit-msg-check /opt/git-templates/hooks/commit-msg
chmod +x /opt/git-templates/hooks/commit-msg

git init --template=/opt/git-templates
```

这样每个新仓库自带 `commit-msg` 校验，不需要再跑 `core.hooksPath` 配置。模板目录里还可以放 `info/exclude`（默认忽略规则）和 `description`。

注意：模板只在 **init 那一刻**复制，之后修改模板不会影响已有仓库。

## --separate-git-dir：把 .git 放到别处

```bash
git init --separate-git-dir=/data/repos/myproject.git /work/my-project
```

工作目录里只会有一个 `.git` 文件（内容是一行 `gitdir: /data/repos/...`），真正的仓库数据在别处。适合「代码目录在 SSD、对象库在大盘」或「工作目录会被整体同步覆盖」的场景。

## 已有项目接入 Git 的完整顺序

```bash
cd existing-project
git init -b main

# 先建忽略规则，再 add，否则会把 node_modules 之类一起塞进暂存区
printf 'node_modules/\n.env\ndist/\n' > .gitignore

git add .
git status --short | head    # 确认没混进不该提交的东西
git commit -m "chore: initial import"
```

顺序很关键：**先写 `.gitignore` 再 `git add .`**。反过来做，已经暂存的文件不会因为补了忽略规则而自动移出，需要 `git rm -r --cached .` 重来。

首次提交前的自查：

```bash
# 是否混入了大文件或密钥
git ls-files | xargs -I{} du -h {} 2>/dev/null | sort -rh | head
git ls-files | grep -Ei '\.(env|pem|key)$'
```

## 常见错误

**以为 init 等于 clone**。`git init` 建的是空仓库，没有远端、没有历史、没有分支（`HEAD` 指向一个尚不存在的分支）。要接入已有项目，用 `git clone`。

**在错误的目录层级 init**。在 `~/projects` 这个装着几十个项目的父目录里 init，会把所有子项目都纳进一个仓库。发现后删掉 `.git` 即可，但删之前确认里面没有你以为已经提交的东西。

**忘记 -b 导致分支名和团队不一致**。这不会报错，但推送时会出现「本地 master、远端 main」两套分支并存的情况，后续要手动改名。
