# git-gc 教程

## gc 到底做什么

`git gc` 是一组维护操作的合集：松散对象打包（`git repack`）、按 `gc.pruneExpire`（默认 2 周）清理不可达对象、清理 reflog 过期项、合并过小的 pack。它和 `git count-objects -v` 是配套的——那边读出「松散对象 8000+」，这边就是处理动作。

```bash
git gc                 # 常规维护：打包 + 按 2 周宽限清理
git gc --aggressive    # 更彻底的 delta 重算，慢很多；偶尔跑一次即可
git gc --prune=now     # 立即清理不可达对象（跳过 2 周宽限）
git gc --auto          # 只在超过 gc.auto 阈值时才干活，适合放进 cron
```

## 什么时候需要手动跑

- **rebase / amend / reset 高频之后**：旧提交都还在对象库里占空间，`git count-objects -v` 的 `count` 超过几千就该收了。
- **归档或备份前**：先 gc 能把备份体积压到最小，也让备份里的 pack 结构干净。
- **CI 容器里的浅仓库**：自动 gc 常被跳过，定期 `git gc --auto` 显式触发。

## --prune=now 的风险

`git gc --prune=now` 会**立即物理删除**所有不可达对象——包括你 reset 丢掉、本可以救回来的提交。跑之前想清楚：reflog 里还有没有要找的东西？不确定就先 `git fsck --unreachable` 看一眼不可达对象列表，或者老老实实用默认 2 周宽限。

另一个常见坑：gc 运行期间会锁仓库（`.git/gc.pid`），期间别的 Git 命令会报锁冲突。长仓库的 gc 放后台跑，别在发版窗口执行。

## 边界

- gc **不能给仓库瘦身**——它只整理「当前历史引用到的」对象；体积大是因为历史里有大的二进制时，需要 `git filter-repo` 改写历史，gc 帮不上。
- `--aggressive` 的收益经常被高估：多数仓库跑完体积几乎不变，白白多等几十分钟。delta 压缩参数（`pack.window`、`pack.depth`）通常比它更值得调。
- 正常个人开发仓库几乎从不需要手动 gc；自动 gc 的触发线（松散对象约 6700 个）日常够用。
