# git-cat-file 教程

## 先想一个问题

直接 `cat .git/objects/...` 看到的是一串 zlib 压缩的二进制。`git cat-file` 是把它解开的入口，也是核对对象类型、大小、内容最直接的手段。它纯只读，但要求你先知道自己查的是 blob、tree、commit 还是 tag——类型不对，`-p` 的输出就完全看不懂。

## 四种对象的查看方式

```bash
# 1. blob：某次提交里某个文件当时的完整内容（不是 diff）
git cat-file -p HEAD~3:src/config.ts

# 2. tree：某个目录在那一刻的列表（文件名 → blob hash）
git cat-file -p HEAD^{tree}
git cat-file -p HEAD:src

# 3. commit：元数据 + 根树 hash + 父提交
git cat-file -p HEAD

# 4. tag：annotated tag 对象（指向哪个 commit、打标签的人和时间）
git cat-file -p v1.0.0
```

路径语法 `commit:path` 里的 path 是**相对仓库根目录**的，不像 shell 命令相对当前目录——在子目录里执行 `git cat-file -p HEAD:./file` 才是相对路径。

## 先问类型再看内容

拿到一个 hash 不知道它是什么时，先跑 `-t`（type）和 `-s`（size in bytes），再看内容：

```bash
$ git cat-file -t 3b18e51
blob
$ git cat-file -s 3b18e51
1247
```

这两个命令是脚本里最常用的形态——不输出内容、只回答「这是什么、多大」，速度比 `-p` 快得多。

## 脚本友好的批量输出

`--batch-check` 从 stdin 批量读对象名，一行一个，输出 `hash type size`：

```bash
# 找出仓库里所有超过 10MB 的 blob（大文件排查的经典组合）
git rev-list --objects --all \
| git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
| awk '/^blob/ && $3 > 10000000 {print $3, $4}'
```

`%(rest)` 会带上 `rev-list --objects` 输出里对象名后面的文件路径，所以最后一列直接可读。这是「仓库为什么这么大」类问题的标准起手式，比 `git count-objects` 的总量统计精确到单个文件。

## 报错与边界

```
$ git cat-file -p abc1234
fatal: Not a valid object name abc1234
```

两种常见触发：hash 写短了撞上不存在的对象，或者对象只在别的引用里而你当前仓库 fetch 不到。先用 `git cat-file -t` 确认存在性，再处理内容。

- **纯只读**，任何形式都不修改仓库状态，可以在任何时刻安全运行。
- `-p` 对 blob 输出原始内容；想看「这个 blob 和哪个版本差在哪」，那是 `git diff` 的事，`cat-file` 不做比较。
- 写脚本时优先用 `--batch-check` 而不是循环调用单对象命令——前者一次进程搞定，后者每个 hash 起一个进程，慢一个数量级。
