# GitLab 受保护分支与审批规则

## 学完这篇你会掌握什么

- 在 GitLab 里为 `main` 配置一套可直接落地的保护规则：禁止直接 push、强制 MR、必需 CI 和审批
- 分清 Maintainer / Developer 角色在 Allowed to merge / Allowed to push 里的分工逻辑
- 用 Approval rules 把"至少 N 个人点头"变成平台强制，而不是群里喊一嗓子

## 先想一个问题

想象一个场景：周五晚上，一位新同事为了"赶紧修个线上小问题"，直接往 `main` push 了一个没跑过 CI 的提交。十分钟后流水线红了，同组的发布被卡住，没人说得清这个提交改了什么。

问题不在人，在于 `main` 对所有人敞开。受保护分支解决的就是这件事：**把"大家约定好别直接推"升级成"平台根本不允许推"**。这篇带你把 GitLab 的 Protected branches 和 Approval rules 配置成一套能实际运转的门禁。

## 一句话理解

受保护分支决定"谁能往这条分支送代码、走什么流程"；审批规则决定"MR 合并前必须满足哪些人的同意"。两者配合，`main` 才真正变成一条只能通过评审进入的分支。

## 动手配置最小保护规则

进入项目 **Settings → Repository → Protected branches**，点 **Add protected branch**（或 **Expand** 展开已有列表），对 `main` 做如下配置：

| 配置项 | 推荐值 | 说明 |
| --- | --- | --- |
| Branch | `main` | 通配符可用，如 `release/*` |
| Allowed to merge | Maintainers | 谁有权限点合并按钮 |
| Allowed to push and merge | No one | 任何人都不许直推，只能走 MR |
| Allowed to force push | 关闭 | 防止改写公共历史 |

配置完成后立刻验证：本地往 `main` 直推一次。

```bash
git checkout main
git commit --allow-empty -m "test direct push"
git push origin main
```

终端会收到拒绝：

```text
remote: You are not allowed to push code to this branch.
To gitlab.example.com:team/app.git
 ! [remote rejected] main -> main (protected branch hook declined)
error: failed to push some refs to 'gitlab.example.com:team/app.git'
```

看到 `protected branch hook declined` 就说明门禁生效了。

<WarningBox title="Allowed to push 不要留 Developers">
  给 Developer 保留直推权限是常见的"配置了等于没配"：保护规则只拦 Maintainer 之外的人。想让所有人走 MR，就把 Allowed to push and merge 设为 No one。
</WarningBox>

## 用审批规则强制"至少两个人点头"

分支保护解决了"怎么进"，审批规则解决"谁来把关"。入口在 **Settings → Merge requests → Merge request approval rules**。

**默认审批规则（全仓库生效）**：把 Approvals required 设为 `1` 或 `2`，Approval rules 选 **Any eligible users**（任何有权限的人都可以审）或指定审批人。

**按模块定向审批**：点 **Add approval rule**，可以按 Code owners 路径规则定向——比如 `frontend/**` 需要 `@frontend-team` 里的 2 个人同意，`infra/**` 需要 `@sre` 的 1 个人同意。谁改了哪块代码，GitLab 会按改动文件自动算出该找谁审。

配置完成后，一个不满足审批数的 MR 会在合并按钮旁边明确显示：

```text
Merge blocked: 1 approval required but 0 given.
```

## 常见误区

- **把审批数设成 3、4 个起步**：审批人凑不齐，MR 堆积，大家开始互相"无脑点同意"，评审质量反而下降。小团队 1 个、核心模块 2 个是更可持续的起点。
- **保护了 `main` 却放过 `release/*`**：发布分支同样直接面向生产，用通配符 `release/*` 一起纳入保护。
- **审批规则从不更新**：同事离职后还留在 Approvers 列表里，审批请求发给了不存在的人。每次组织调整后过一遍规则。

## 和工作流怎么配合

保护分支 + 审批规则只定义了"门禁"，日常怎么走还取决于团队流程：

- 小团队直接用 GitHub Flow 式的"分支 → MR → 评审 → 合并"节奏即可
- 需要区分发布节奏的团队，配合 GitLab Flow 的环境分支使用
- 高流量的 monorepo 可以进一步开启 Merge Trains，让合并本身也排队验证

<TipBox title="落地顺序建议">
  先上"禁止直推 + 1 个审批"这两个最小项，跑两周稳定后再按模块加定向审批规则。一次把所有门禁拉满，最常见的结局是团队想办法绕过门禁。
</TipBox>
